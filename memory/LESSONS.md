# LESSONS — durable rules the desk has learned (consult before trading)

Seeded with priors from the strategy. Add to this whenever a trade teaches something. Keep each lesson as a rule that changes future behavior.

## Starting priors
- **The core is the edge.** 70% in SPY means we start each week nearly matching the index. Don't jeopardize that reliability chasing satellite thrills.
- **Cut fast, let winners run.** Trailing stops exist so losers are small and winners are large. Never widen a stop; never average down.
- **A thesis or no trade.** If you can't write one falsifiable line for why, skip it. Boredom is not a signal.
- **Respect the caps.** The 5%/position, 3-per-week, and 3% daily loss cap are the difference between a strategy and gambling. The script enforces them — treat a rejection as wisdom, not an obstacle.
- **Beating SPY is hard.** Most active trading underperforms. Assume the burden of proof is on every satellite trade to justify its risk over just holding the index.
- **Don't revenge-trade.** After a stop-out, the next trade must clear the same bar as any other. Emotion is the enemy.

## Learned lessons
- **Never wrap an order-submitting command in a shell `||` fallback.** On 2026-07-08 a `python3 scripts/alpaca.py buy XLF ... || python scripts/alpaca.py buy XLF ...` pattern (used to try `python3` then fall back to `python`) caused a duplicate live buy: the first invocation submitted the market order successfully but exited non-zero when the trailing-stop attach step hit a transient race ("cannot open a short sell while a long buy order is open"), so the `||` triggered the second invocation, which submitted a second full buy order. Result: a satellite position at ~7.9% of equity (over the 5% cap) and a double-counted weekly slot, both caught and corrected after the fact only by manually checking `positions`/`orders` against intent. Fix: run buy/sell/stop commands as a single invocation (pick one interpreter and commit to it, e.g. probe with `python3 --version` once, or just run `python3 ...` and report failure rather than silently retrying with a fallback). If a command exits non-zero after "submitted" appears in its output, check live `positions`/`orders` before doing anything else — do not assume it's safe to retry.
- **The same 403 "cannot open a short sell while a long buy order is open" error also fires for a legitimate reason: a slow paper-market fill outlasting the script's 15s wait.** On 2026-07-09 the `buy XLK` command hit this exact error, but `orders` showed the buy order genuinely still `new`/`partially_filled` (not a duplicate) — it finished filling ~30s after submission. Confirmed this was not a repeat of the 2026-07-08 duplicate-order bug (`counters.json` stayed correctly at +1). Fix in this case: don't retry the buy; poll `orders`/`positions` until the buy shows fully filled (no open buy order left, position qty matches intended), then attach the trailing stop manually with `scripts/alpaca.py stop SYMBOL --trail-percent N`.
- **An overbought RS flag (RS>70) that appears shortly after a satellite entry is a cue to tighten the stop, not just a note to "watch."** XLV (entered 2026-07-07) was flagged RS>70/overbought on 2026-07-08, one day after entry, and then faded to -2.4% by 2026-07-10 without ever tightening its stop off the default 10%. The strategy already calls for tightening trails on "extended winners at midday" — the same logic applies when a fresh entry gets flagged overbought and then stalls: don't wait passively for the default 10% trail to be tested, proactively tighten (e.g. to 6-8%) per `scripts/alpaca.py stop SYMBOL --trail-percent N` the next time this pattern repeats.
- **`scripts/alpaca.py stop SYMBOL --trail-percent N` cannot retighten an *existing* trailing stop — it will be rejected.** Tried on 2026-07-14 to tighten XLV's stop from 10% to 7% after a sharp -3.9% single-day move; Alpaca returned a 403 (`insufficient qty available... held_for_orders`) because the original stop order already holds all the shares as sell-side inventory, and there is no cancel/replace subcommand in `scripts/alpaca.py` to free them first. Do **not** work around this by calling the Alpaca REST API directly (cancelling an order that way is exactly the kind of raw-call workaround the operating instructions forbid) — instead leave the existing stop live (it's still a valid safety net) and flag the gap in `memory/STATE.md`/here. This needs a proper fix: add a `cancel`/`replace-stop` subcommand to `scripts/alpaca.py` (cancel the old trailing-stop order by ID, then submit the new one) so future routines can actually retighten stops on flagged laggards instead of only being able to attach a stop once.
- **The same "no cancel/replace" gap also blocks a full discretionary exit, not just stop-retightening.** On 2026-07-17, XLK's thesis broke cleanly (price below its tracked 50-day MA for multiple sessions, confirmed worsening chip-sector rout) and the strategy's "midday discretionary cut" rule called for closing it early. `scripts/alpaca.py sell XLK --all` was rejected with the identical 403 `held_for_orders` error — a resting trailing-stop order holds 100% of the shares, so **no sell of any kind (discretionary or otherwise) is possible on a satellite position while its trailing stop is live**, only the stop itself can ever close the position until this is fixed. Left XLK open with its original stop, did not work around it via raw API. This is a second, independent confirmation that `scripts/alpaca.py` needs a cancel-order subcommand — without it, the desk's discretionary-exit discipline (a core part of the strategy) is currently non-functional for any position past its initial entry.
- **This gap is now confirmed structural (three occurrences: XLV retighten 7/14, XLK exit attempt 7/17 pre-open flag, XLK exit attempt 7/17 open), so the desk must change behavior around it, not just keep flagging it.** Until `scripts/alpaca.py` gets a cancel/replace-order subcommand: (1) treat every new satellite entry as effectively **un-cuttable except by its own trailing stop** once the stop is attached — factor that into the entry bar (size and conviction) since "we can exit early if the thesis breaks" is not currently true in practice; (2) for a position whose thesis breaks and can't be sold, consider whether tightening is somehow achievable, and if truly nothing is actionable, explicitly say so in `STATE.md` rather than repeatedly re-attempting the same rejected sell each routine; (3) escalate this as the top engineering priority in every weekly review until it's fixed — it sits directly on the critical path of the strategy's exit discipline.
- **A fifth confirmed occurrence (XLK exit attempt 7/23) and three consecutive weekly reviews (7/10, 7/17, 7/24) re-flagging the same gap in the abstract means "keep flagging it" has failed as a strategy — the next flag needs to carry the fix, not just the symptom.** Root cause, worked out 2026-07-24: `cmd_sell --all` calls Alpaca's `DELETE /v2/positions/{symbol}`, and `cmd_stop` always POSTs a brand-new trailing-stop order; neither ever cancels the symbol's existing resting order first, so Alpaca refuses because the shares are already committed (`held_for_orders`). `scripts/alpaca.py` already has `get_open_orders()` but no `cancel_order(order_id)` (`DELETE /v2/orders/{id}`) and no CLI `cancel` subcommand. The fix — add `cancel_order`, and cancel any open order on the symbol before submitting a new stop or a full sell — doesn't touch `risk.py` or bypass any guardrail; it only unblocks exits/retightens on positions that already passed risk checks at entry. Lesson: when a tooling gap survives three-plus re-flags, the next mention of it should include the concrete fix (root cause + smallest patch), not another restatement of the symptom, so a human reviewing the memory can act on it in one pass.
- **The un-cuttable-position fallback ("wait for the trailing stop to fire on its own") works, but it has a quantifiable cost — this is no longer an abstract complaint.** XLK's thesis broke 2026-07-17 and a discretionary cut was correctly attempted and blocked by the `scripts/alpaca.py` cancel/replace gap on 07-17 and 07-23 (position then at -3.9% to -5.4%). It finally closed via its own 10% trailing stop on 07-28 at roughly -7% — about 2-3 extra points of loss, ~$100-130 (~0.1% of equity) on a position sized under the 5% cap, directly attributable to the unfixed gap. Small this time only because sizing discipline capped the position; a larger position or slower-firing stop would cost proportionally more. This is the fourth consecutive Friday review (07-10, 07-17, 07-24, 07-31) flagging the same root cause and fix (already fully specified in the 2026-07-24 entry below). No routine can edit `scripts/alpaca.py` itself — further routines should keep the flag short (cite this entry) rather than re-deriving the root cause each time, and treat this as an item for the human operator to actually patch.
- **A trailing stop is a stop-*market* order, not stop-limit — on a genuine overnight guidance gap it will fill well through its trigger price, and that's working as intended, not a bug.** AAPL's 8% trail (entered $327.57, HWM $344.57 → trigger $317.00) stopped out 2026-07-31 after Apple's fiscal Q3 guidance cut, but the fill printed at $301.82 — ~4.7% below the trigger — because the stock gapped straight through it at the open rather than trading down to it tick by tick. Net realized loss was -7.86%, close to the pre-market print (-6.65% to -7.3%), i.e. the stop captured the move about as well as any stop could on a real overnight gap. Lesson: don't read a large stop-trigger-to-fill gap as a tooling problem or a reason to second-guess the stop mechanism — it's the expected cost of using market-based trailing stops through binary catalysts (earnings), and it's still far better than not having a stop. Sizing satellite positions ≤5% and never averaging down is what keeps a single gap like this small relative to the book (~0.31% of equity here).
- **Settled cash, not margin/`buying_power`, is the real constraint on sizing a new satellite entry — this was repeated correct improvisation across several routines (2026-08-05, 08-06, 08-07) but never written down as a rule until now.** Each of those days, `buying_power` showed ~$287,810 available (margin) while actual cash sat at ~$1,699 — well short of the ~$4,100-5,100 a compliant new ~4-5% position needs — and each routine correctly declined to size a trade off margin, flagging it in `IDEAS.md`/`STATE.md` instead of acting on it, since levering the satellite sleeve beyond what cash supports is a policy change no single routine has authority to make unilaterally. Codifying it: **only settled cash counts as available capacity for a new satellite entry.** Margin/`buying_power` headroom does not authorize sizing past what cash supports, absent an explicit instruction from the human operator to change this policy. If cash is genuinely the binding constraint, the correct moves are to wait for a stop-out/trim/rebalance to free it, or flag the constraint — not to reach for margin.
- **A "compliant" satellite entry does not require matching the size of prior entries — `risk.py`/`risk.yaml` enforce only a 5% *maximum*, with no enforced minimum.** By the 2026-08-21 weekly review, cash had sat flat at $1,699.14 for 16 straight calendar days, and every routine in that stretch treated the ~$5,100 needed for a "typical" ~4-5% entry as the bar for *any* new entry — nothing in the code actually requires that; a smaller position (e.g. ~1.6% of equity, sized to whatever cash is actually available) is just as compliant. Going forward: when cash-constrained, don't default to "no entry possible" — check whether a smaller, cash-sized position on the top-conviction idea is worth taking, and if the desk judges a sub-2% position too diluted to bother with, that should be an explicit, stated policy call (ideally from the human operator) rather than an unexamined assumption repeated routine after routine.
- **A persistent, multi-day constraint (cash lockout, an unresolved tooling gap) deserves a direct, specific recommendation at the next weekly review, not another passive restatement.** The 2026-08-21 review made an explicit ask of the human operator (set a minimum satellite-size floor, or authorize cash-sized entries) instead of repeating "cash remains constrained" for the umpteenth routine. When a Friday review inherits a standing item that's been flagged many times running, use that checkpoint to escalate to a concrete decision point, not just log it again.
- **Check that the weekly review actually ran the prior week before writing this one.** On 2026-08-21, `memory/WEEKLY.md` had no entry for 2026-W33 (2026-08-10 to 2026-08-14) — the log jumped from W32 straight to W34, meaning a scheduled Friday review apparently didn't fire (echoing the 2026-08-07 pre-market-skip finding). Each Friday review should grep/skim `memory/WEEKLY.md` for the immediately preceding ISO week and flag a gap explicitly if it's missing, rather than silently reviewing only the current week as if nothing was skipped.
- **`memory/STATE.md`'s "Notes for the next routine" section had silently grown into a full duplicate of `memory/JOURNAL.md`** (50+ historical bullets going back to deploy day, one file needed by every single routine's mandatory first read). Since `JOURNAL.md` is already the permanent append-only record, nothing was lost by trimming `STATE.md`'s notes list down to roughly the 5 most recent entries on 2026-07-29. Going forward: keep that section to a handful of recent entries and trim it again whenever it re-accumulates — `STATE.md` is a live snapshot for handoff, not a second history file, and letting it re-grow just taxes every future routine's context for no benefit.
- **A stuck escalation can resolve itself through an unrelated later decision — check before assuming it still needs an explicit answer.** The 2026-08-21/08-28 cash-lockout escalation (asking the human operator to set a minimum satellite-size floor or authorize cash-sized entries) never drew a direct response, but the 2026-08-28 core tilt (70/30 → 60/40, trimming SPY toward 60%) freed enough cash as a side effect that by 2026-09-03 the desk was back to sizing normal ~4% entries (JPM, XLB) under real theses, with no cash constraint at all. The lesson isn't "escalations don't matter" — it's that before repeating an old escalation verbatim, check whether a later, unrelated action already mooted it; an escalation that's actually resolved should be marked resolved in the next weekly review, not carried forward as an open item out of habit.
- **Three consecutive weekly readings in the same direction is a trend, not noise, even when every individual week's process was clean.** Since-inception alpha widened every Friday from 2026-08-21 (-0.59%) through 2026-08-28 (-0.91%) to 2026-09-04 (-1.16%) — each week individually had zero guardrail breaches and sound theses, so no single week's review had cause to downgrade sharply. But three straight weeks of the same directional move is itself a signal worth weighting in the grade and flagging explicitly, independent of whether that week's decisions were good — a strategy can execute its process perfectly and still be the wrong strategy at its current sizing/conviction bar. When a metric moves the same direction three-plus Fridays running, say so plainly in the grade rationale rather than only in the performance section, and set an explicit trigger (e.g. "if it widens a fourth week, escalate") rather than a passive "worth watching."
- **A single stuck, unanswered operator escalation can persist indefinitely if every routine just repeats it verbatim — verify the underlying state, don't only re-flag it.** The 2026-08-21 weekly review made a direct, specific ask (a minimum satellite-size floor, or authorization to size to available cash); a full week and roughly twenty routines later (through 2026-08-28) it had drawn no response, but nothing changed in how it was flagged — each routine just restated the same paragraph. Two things going forward: (1) when a recommendation goes unanswered past one full weekly cycle, the next review should decide explicitly whether to escalate further, rephrase as a narrower yes/no question, or treat continued silence as an implicit decision — not just repeat the identical ask a third or fourth time unchanged; (2) separately, on 2026-08-28 the EOD routine found the shared memory branch (`origin/claude/desk`) four days stale versus this session's own history — a real, structural risk (a fresh clone would have lost four days of state) that was flagged but whose root cause was never diagnosed, even though it self-resolved by that evening's commit. Don't let a resolved-looking symptom close the loop on an undiagnosed root cause — if `commit_memory.py` ever again appears not to land on the shared branch, that's worth investigating properly (is `MEMORY_BRANCH` reliably set? did a prior routine push to the wrong ref?) rather than assuming the next successful push fixed it for good.
